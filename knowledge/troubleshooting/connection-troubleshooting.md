# RDS 连接问题排查

RDS 连接失败的排查有一条固定顺序：**白名单 → 账号与权限 → 网络可达 → 连接数**。这个顺序不是随意排的，它按「发生频率 × 排查成本」递减——白名单问题占了实际工单的大多数，而看连接数只需要一条命令。跳序排查最容易导致的后果是：改了半小时安全组，其实只是 IP 没加白名单。

## 第零步：先看清错误信息

不同客户端报的是同一件事的不同侧面，但 MySQL 的错误码几乎能直接定位到下面四层中的哪一层：

| 错误 | 含义 | 优先看 |
|---|---|---|
| `ERROR 2003 (HY000): Can't connect to MySQL server on 'xxx' (110/111)` | TCP 都没连上 | 网络可达 / 白名单 |
| `ERROR 2003 ... (60)` (macOS) / 长时间无响应 | 超时，包被丢弃 | 白名单（最典型） |
| `ERROR 1045 (28000): Access denied for user 'x'@'y'` | TCP 通了，认证失败 | 账号密码 / 授权主机 |
| `ERROR 1044 (42000): Access denied for user ... to database` | 认证通过，库权限不足 | 账号授权 |
| `ERROR 1040: Too many connections` | 连接数打满 | 连接数 |
| `Lost connection to MySQL server during query` | 连上后断开 | 超时参数 / 网络抖动 |

`(111) Connection refused` 与 `(110) Connection timed out` 值得区分：refused 说明端口对面有东西在主动拒绝（多半是地址或端口写错、或实例处于异常状态）；timed out 说明包发出去石沉大海，几乎总是白名单或网络路径问题。

## 第一层：白名单

RDS 的 IP 白名单在实例侧独立存在，与 ECS 安全组是两套东西，互不相通。控制台路径：实例 → 数据安全性 → 白名单设置。

**检查要点：**

- 客户端**真实出口 IP** 是否在内。这句话的实操含义是：如果应用部署在 ECS 上而 ECS 走 NAT 出公网，需要加的是 NAT 网关的公网 IP，不是 ECS 自己的地址。在应用所在机器上执行 `curl ifconfig.me` 或 `curl 100.100.100.100/latest/meta-data/eipv4`（VPC 内元数据接口，不走公网）来确认。
- 是否误加了 `0.0.0.0/0`。它能连上，但等于把数据库暴露在公网扫描之下，属于必须整改的配置，不能当作排障手段遗留。
- 分组是否选对。白名单支持多个分组，**生效的是当前应用连接所属网络环境对应分组**，新加的条目落在错误分组里不会生效。
- 是否填了裸 IP 而非 CIDR。`192.168.1.100` 合法，但历史版本对不带掩码的写法处理不一致，统一写 `192.168.1.100/32` 更稳。

验证是否卡在白名单，最直接的办法是在已授权的机器上试连，而不是在同一台未授权的机器上反复改密码。

## 第二层：账号、密码与权限

`Access denied for user 'app'@'10.0.0.5' (using password: YES)` 里的 `'app'@'10.0.0.5'` 是 MySQL 的**账号+来源主机组合**，而不是单纯的账号名。RDS 高权限账号与普通账号的授权主机不同，常见坑：

- 在控制台创建了账号 `app` 并授权了来源 `%`，但应用侧用了另一个同名不同主机的账号。
- 密码里含特殊字符（`#`、`$`、`!`、`&`），在 shell 命令行或 URL 连接串里被截断或转义。用单引号包裹，或在连接串里做 URL 编码；怀疑时先用 `mysql --defaults-extra-file` 走配置文件绕过 shell 解析。
- 账号被锁定（多次错误密码触发）。控制台的账号状态里能看到，解锁即可。
- 只授予了某个库的权限，应用连的是另一个库（对应 `ERROR 1044`）。

RDS 的账号权限在控制台「账号管理」里管理，命令行 `GRANT` 在高权限账号下也可用，但要清楚二者是同一天平的两端。

## 第三层：网络可达

到这一层才真正涉及网络路径。**核心判断：内网地址还是外网地址。**

RDS 实例默认只有内网地址（VPC 内可达）。内网地址从 VPC 外的机器连不上，也不会有明确报错，只有超时。要用外网连接，必须在控制台「数据库连接」里**显式申请外网地址**，并且应用侧改用外网域名。

检查顺序：

```bash
# 域名解析出什么地址
nslookup rm-xxxxxx.mysql.rds.aliyuncs.com
# TCP 是否通
nc -vz rm-xxxxxx.mysql.rds.aliyuncs.com 3306
```

解析失败说明用的地址本身不对（常见于把内网域名拿到公网机器上解析）；解析成功但 `nc` 不通，回到白名单或安全组。

**端口**：RDS 默认 3306，但支持修改，历史实例可能不是默认端口，以控制台连接信息为准。

**跨 VPC / 经典网络**：内网地址只在同一 VPC 内可达。应用与 RDS 不在同一 VPC 时，需要走云企业网或对等连接打通，或直接走外网地址。这类问题的典型特征是「同样的配置在别的机器上是通的」。

## 第四层：连接数

`Too many connections` 说明前面三层都没问题，只是实例并发额度满了。RDS 的 `max_connections` 与实例规格绑定，规格越小上限越低，可以在控制台参数设置里查看与调整（调整上限不解决根因）。

先看实际占用：

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';
SHOW PROCESSLIST;
```

`SHOW PROCESSLIST` 输出里若大量连接停留在 `Sleep` 状态，说明连接池没有归还连接。这时先看应用侧的连接池配置（`pool size`、`idle timeout`、连接最大存活时间），而不是先扩 `max_connections`——扩了只是把撞墙的时间往后推。

另一个高频原因是连接池「拿到失效连接」。RDS 侧的 `wait_timeout` 会断开长时间空闲连接，而客户端连接池不知道，于是把已死的连接交给业务。表现为间歇性 `Lost connection` 或首次请求慢、重试成功。解决方式是开启连接池的有效性检测（如 Druid/HikariCP 的 `testOnBorrow` / 定期探活），并把连接池的最大空闲时间设置得比 `wait_timeout` 短。

## 兜底：确认实例本身状态

如果以上四层都排除了，检查实例是否处于正常服务状态：控制台实例状态是否为「运行中」，是否有进行中的小版本升级、备份任务或主备切换。主备切换期间会短暂出现连接中断，属于预期行为，应用侧的连接重试逻辑应当覆盖它。

存储打满也会导致连接异常（写入被拒、实例锁定），这属于另一类问题，看监控里的磁盘使用率即可排除。

## 一句话流程

**读错误码 → 确认出口 IP 已加白名单 → 确认账号+来源主机+密码三者匹配 → 内/外网地址用对并 `nc -vz` 验证 → 最后才看连接数**。顺序颠倒时，最常见的浪费是在网络层反复试一个根本没加白名单的连接。
