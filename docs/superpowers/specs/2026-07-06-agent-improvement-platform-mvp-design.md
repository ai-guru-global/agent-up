# Agent 改进平台 — MVP 设计文档

- **状态**: Draft（待用户审阅）
- **日期**: 2026-07-06
- **范围**: 子项目 B（产品组 Agent 改进工作台）+ 子项目 D（统一 Web UI 门户）的 MVP
- **首发范围决策**: 先做 B+D 的 MVP，反馈数据纯手动录入；子项目 A（数据采集层）、C（进化与洞察层）后续各自走设计循环
- **架构方案**: 方案 A — 以 Agent 配置为中心（"一个 agent = 一个配置面板"）

---

## 1. 背景与设计理念

### 1.1 业务背景

我们是专有云工单团队，向各云产品输出各自产品线专属的 agent，供 CRE（类似 SRE）使用。这些 agent 是**中心部署**的，各专有云现场的 CRE 通过群聊或 Web 页面与 agent 互动。现场客户通过提工单、在工单群与 agent 互动。**关键约束：agent 没有访问现场专有云的权限**——agent 是"在岗顾问"，不是"远程操作员"。

### 1.2 三层 Loop 设计理念

本平台以**三个不同时间尺度的产品改进循环**为骨架：

| Loop | 名称 | 时间尺度 | 在本场景的含义 | MVP 覆盖 |
|------|------|---------|--------------|---------|
| **L1** | 即时交互环（Runtime Loop） | 分钟级 | CRE / 客户通过群聊或 Web 与中心 agent 实时互动，处理工单。agent "在岗解决问题"。 | 本平台**不直接实现 L1 运行时**，只承接 L1 产生的反馈（手动录入） |
| **L2** | 产品改进环（Developer Feedback Loop） | 小时～天级 | 各产品组基于 L1 反馈（会话、评分、失败案例）维护改进自己的 agent：更新 prompt、蒸馏知识、配置工具、调整路由，提交发布。 | **MVP 核心** |
| **L3** | 智能进化环（Evolution Loop） | 天～周级 | 跨 agent、跨现场的问题总结，发现共性、沉淀能力、驱动 agent 自进化。 | MVP 不做；但 B 的数据模型为 C 预留扩展点（见 §5.3） |

### 1.3 Agent 全生命周期作为上下文

"全生命周期"不是抽象口号，而是平台的核心数据线索：从 agent 上线 → 被使用 → 收集反馈 → 改进 → 再上线的闭环中，每个阶段的**上下文**（会话反馈、知识状态、配置变更、版本历史）都沉淀为可追溯的数据。平台用 **Release（发布记录）+ Version（版本快照）** 把这条链路串起来，让每一次改进都可解释、可回溯、可回滚。

### 1.4 角色与约束

- **CRE（SRE）**：使用者。与 agent 互动处理工单，可查看会话反馈、提改进建议。
- **现场客户**：使用者。通过工单与 agent 互动，不直接进平台。
- **各产品组**：维护各自产品线的 agent，编辑配置、提交发布。
- **工单团队**：平台运营方，审批 agent 变更、运营整个平台。
- **关键约束**：agent 中心部署，无现场专有云访问权限。

## 2. 核心架构：方案 A — 以 Agent 配置为中心

### 2.1 方案选型

经过对比三个候选方案，选定方案 A：

- **方案 A（选定）：以 Agent 配置为中心** — 每个 agent 是一个"配置中心"页面，四个分区（Prompt / 知识库 / 工具 / 路由）作为页内 Tab。直观、心智简单。
- **方案 B（未选）：以"变更工单"为中心** — 每次改进 = 一个变更工单，关联证据、修改、审批。链路最完整但多一层操作。
- **方案 C（未选）：Git 化配置仓库** — 配置即文件，改进即 PR。开发者熟悉但非开发角色学习成本高。

**选方案 A 的关键考量**：产品组/工单团队多为非开发角色，"一个 agent = 一个配置面板"心智最轻，落地阻力最小。

### 2.2 方案 A 如何满足"全生命周期上下文"

方案 A 不把"一次改进"显式建模成独立实体（那是方案 B 的做法）。本设计通过 **Release（发布记录）** 轻量补足"为什么改"：

- 产品组点"提交发布"时，必须填**改进说明** + **可选关联 Feedback**。
- 审批通过 → 冻结为一个 Version 快照 → 可回滚。

这样反馈 → 修改 → 版本这条链路仍然可追溯，只是不强制走"建工单"流程，保持了方案 A 的轻量。

## 3. 数据模型

四个核心实体。

### 3.1 Agent（产品组维护的对象）

归属某个产品组。一个 Agent = 一份配置，包含四个分区：

#### 3.1.1 `prompt` 分区 — 系统提示词
系统提示词、角色设定、指令、约束。纯文本（含 Markdown），是 prompt 工程的主战场。

#### 3.1.2 `knowledge` 分区 — Wiki 知识层（两层知识架构之上层）

> ⚠️ **关键设计**：知识不是"一桶平铺文档"，而是基于 llm-wiki 模式的**蒸馏态知识网**。

`knowledge` 分区指向一个 **Obsidian wiki vault**（markdown 页面集合）。运行时 agent **优先检索 wiki**（遵循 llm-wiki "Compile, don't retrieve" 理念）。产品组通过 wiki 工作流维护它：

| 维护操作 | 对应工作流 | 作用 |
|---------|-----------|------|
| 蒸馏新源 | `wiki-ingest` | 把文档/会话/FAQ 蒸馏成 wiki 页面 |
| 更新页面 | `wiki-update` | 修订现有页面内容 |
| 跨页综合 | `wiki-synthesize` | 跨多个页面做综合分析，生成 synthesis 页 |
| 健康检查 | `wiki-lint` | 审计孤立页、矛盾、断链 |

每个 wiki 页面携带质量元数据（来自 llm-wiki 规范）：

- **Provenance（来源标记）**：`extracted`（直接转述，默认）/ `^[inferred]`（LLM 推断）/ `^[ambiguous]`（来源存疑）
- **Lifecycle（生命周期）**：`draft` → `reviewed` → `verified`；可转 `disputed` / `archived`
- **Tier（重要性分层）**：`core`（承重页，总是更新）/ `supporting`（默认）/ `peripheral`（低连接，按需更新）
- **`base_confidence`**：[0.0, 1.0] 信心分，按来源数量与质量加权
- **`[[wikilinks]]`**：页面间互相关联，构成知识网而非文档堆

#### 3.1.3 `tools` 分区 — 工具 / MCP 配置（两层知识架构之下层）

> ⚠️ **明确包含两类工具**：

1. **MCP 工具** — 连接传统知识库 API、底表查询、外部动作。配置项：名称、参数 schema、接入端点、权限范围。这是两层知识架构的**下层数据源连接**：wiki 查不到时，agent 通过这些工具查活数据。
2. **Wiki 查询工具** — 让 agent 运行时检索自己的 wiki vault（对应 llm-wiki 的检索原语：index 预览 → summary 字段 → grep 段落 → 全页读取，逐级升级）。

**两层配合逻辑**：wiki 先答（蒸馏过的高质量知识）；答不到再走 MCP 工具查底表/传统 KB（活数据，但未蒸馏、质量参差）。

#### 3.1.4 `routing` 分区 — 路由 / 策略规则
工单分类路由规则、不同工单类型分派给哪个 agent / 子流程、转人工阈值、升级策略。

### 3.2 Feedback（反馈证据，手动录入）

CRE / 产品组**手动粘贴**的会话片段 + 评分（好 / 差）+ 标签（如"答非所问"、"知识缺失"、"工具调用失败"、"路由错误"）。挂在 Agent 下。

**增强能力**：产品组可把一条 Feedback 直接作为 raw source 喂给 `wiki-ingest`，蒸馏成新 wiki 页面。这样反馈不只触发 prompt / 路由改动，还能**沉淀进知识网**——这是方案 A 框架内实现 agent 自进化（L3）的轻量入口。

### 3.3 Release（发布记录 / 审批单）

产品组点"提交发布"时生成。字段：

- 改了哪个分区（prompt / knowledge / tools / routing 之一或多个）
- **改进说明**（必填）— 一句话说明为什么改
- 关联的 Feedback（可选）
- 审批状态：`pending` / `approved` / `rejected` / `changes_requested`
- 提交人、提交时间
- 审批人、审批时间、审批意见（通过 / 驳回时）

**通过即发布**：审批通过 → 自动生成新 Version 快照。

### 3.4 Version（版本快照，不可变）

每次审批通过并发布，自动生成一个**不可变快照**（语义化版本号 v1.0.0、v1.0.1…）。快照内容：

- 当时的 `prompt` 完整内容
- 当时的 wiki vault 状态指针（vault 快照 / 版本号）
- 当时的 `tools` 完整配置
- 当时的 `routing` 完整配置
- 关联的 Release 记录

任意时刻可**一键回滚**到某个历史版本。Version 序列就是 agent 的"成长轨迹"——全生命周期上下文的主干。

### 3.5 实体关系

```
ProductGroup 1───* Agent
Agent 1───* Feedback        (反馈挂在 agent 下，可被蒸馏进 wiki)
Agent 1───* Release         (发布记录 = 审批单)
Release 1───1 Version       (审批通过 → 冻结为一个版本快照)
Agent 1───* Version         (所有历史版本，可回滚)
```

## 4. 角色与权限

三角色模型（MVP 不引入"现场客户"角色）：

| 角色 | 能做什么 | 不能做什么 |
|------|---------|-----------|
| **工单团队**（平台管理员） | 审批任意 agent 的发布；运营整个平台；管理产品组/CRE 账号；查看全部 agent | — （最高权限） |
| **产品组** | 编辑**本产品组**的 agent 配置（prompt/knowledge/tools/routing）；录入/查看本 agent 的 Feedback；提交发布；查看本 agent 的版本历史 | 不能直接发布（需工单团队审批）；不能编辑其他产品组的 agent |
| **CRE** | 查看 agent 的会话反馈（只读）；提交改进建议（即手动录入 Feedback） | 不能编辑 agent 配置；不能审批 |

**权限隔离原则**：产品组之间相互隔离——ECS 产品组看不到 RDS 产品组的 agent 配置。

## 5. 核心流程

### 5.1 L2 改进闭环（MVP 主流程）

```
① 产品组收到/录入 Feedback
   （CRE 手动粘贴会话 + 评分 + 标签）
        │
        ▼
② 产品组分析 Feedback，决定改什么
   ├─ 改 prompt      → 编辑 prompt 分区
   ├─ 补知识         → wiki-ingest 蒸馏新页 / wiki-update 修订
   ├─ 加/改工具      → 编辑 tools 分区（MCP 端点 / wiki 查询）
   └─ 调路由         → 编辑 routing 分区
        │
        ▼
③ 产品组点"提交发布"
   填改进说明（必填）+ 关联 Feedback（可选）→ 生成 Release（pending）
        │
        ▼
④ 工单团队审批
   看改进说明 + 看 diff + 看关联证据
   ├─ 通过 → 生成新 Version 快照 → 发布生效
   ├─ 驳回 → 打回，产品组重改
   └─ 要求修改 → 产品组修订后重新提交
        │
        ▼
⑤（如出问题）一键回滚到任意历史 Version
```

### 5.2 知识蒸馏子流程（knowledge 分区特有）

```
产品组在 knowledge 分区触发 wiki-ingest
   │  输入 raw source（文档 / 会话 / 一条 Feedback）
   ▼
wiki-ingest 蒸馏 → 生成/更新 wiki 页面
   带 provenance 标记 + lifecycle=draft + tier=supporting
        │
        ▼
产品组人工审阅 → 标记 lifecycle=reviewed / verified
   （可选：wiki-synthesize 跨页综合；wiki-lint 健康检查）
        │
        ▼
随下次 Release 发布，进入 Version 快照
```

### 5.3 为 L3 进化层预留的扩展点

MVP 不实现 L3，但数据模型已为它留好接口：

- **Feedback 聚合**：多条同类标签的 Feedback（如多个 agent 都出现"知识缺失"）可被未来的 C 子项目聚合，发现共性知识缺口。
- **Version 对比**：跨 agent 的版本演进对比，发现哪些改进模式有效。
- **Wiki 跨 agent 复用**：不同 agent 的 wiki vault 可能共享通用概念页（如 [[concepts/ecs-limit]]），未来 C 层可做跨 vault 的知识沉淀。

## 6. Web UI 信息架构（方案 A）

> UI 视觉风格基于 `taste-skill`（`npx skills add https://github.com/Leonxlnx/taste-skill`）。以下为信息架构与页面结构，精细视觉设计在实现阶段用 taste-skill 落地。

### 6.1 顶层导航（按角色区分）

```
┌─────────────────────────────────────────────────────┐
│  Agent改进平台            [@用户名 / 角色]  [退出]    │
├──────────────┬──────────────────────────────────────┤
│  侧边栏       │  主内容区                             │
│              │                                      │
│  ▸ 我的Agent │                                      │
│    ECS-工单  │                                      │
│    RDS-工单  │                                      │
│  ▸ 反馈中心  │                                      │
│  ▸ 发布审批  │  ← 仅工单团队可见                     │
│  ▸ 版本历史  │                                      │
│  ▸ 设置      │  ← 仅工单团队可见                     │
└──────────────┴──────────────────────────────────────┘
```

### 6.2 Agent 配置中心页（核心页面）

"一个 agent = 一个配置面板"，四个分区为页内 Tab：

```
┌─ Agent: ECS-工单Agent  [v1.4.0 当前版本] ────────────┐
│  所属: ECS产品组   状态: 已发布                       │
│                                                       │
│  ┌────────┬──────────┬──────────┬────────┐          │
│  │ Prompt │ 知识库   │ 工具/MCP │ 路由   │ ← Tabs   │
│  └────────┴──────────┴──────────┴────────┘          │
│                                                       │
│  [分区内容编辑区]                                      │
│                                                       │
│  ─────────────────────────────────────               │
│  [提交发布]  [查看版本历史]  [查看反馈]                │
└───────────────────────────────────────────────────────┘
```

**各 Tab 内容**：

- **Prompt Tab**：文本编辑器（Markdown），左右分栏可看上次发布以来的 diff。
- **知识库 Tab**：wiki vault 浏览器——页面列表（按 category 分组）+ 页面详情（provenance/lifecycle/tier/confidence 标记可见）+ [蒸馏新源][更新页面][综合][Lint] 操作按钮。
- **工具/MCP Tab**：工具列表表格（名称 / 类型[MCP|Wiki查询] / 端点 / 参数 / 权限）+ 新增/编辑/删除。
- **路由 Tab**：路由规则表（工单类型 → 分派目标 / 转人工阈值 / 升级策略）。

### 6.3 反馈中心页

Feedback 列表 + 详情。支持按 agent、评分、标签筛选。CRE 角色只能看 + 录入，不能改配置。每条 Feedback 有"蒸馏进知识库"按钮（产品组可见）。

### 6.4 发布审批页（仅工单团队）

待审批 Release 队列。每条展示：改进说明、关联证据、配置 diff（逐分区）、提交人。审批操作：通过 / 驳回 / 要求修改 + 审批意见。

### 6.5 版本历史页

某 agent 的 Version 时间线。每个版本节点：版本号、发布时间、改进说明、关联 Release。支持选两个版本做 diff 对比、一键回滚。

## 7. 技术栈

- **全栈一体框架**（MVP 选型）：前后端同一仓库，开发快。
- **Web UI 视觉**：基于 taste-skill 设计风格。
- **Wiki 存储**：Obsidian 兼容的 markdown 文件（遵循 llm-wiki 规范），版本快照时冻结 vault 状态指针。
- **数据库**：框架自带（如 SQLite / PostgreSQL），存 Agent / Feedback / Release / Version 元数据。

> 具体框架（Next.js / Nuxt / Rails / Django 等）在实施计划阶段结合团队栈最终敲定。

## 8. MVP 范围边界

### 8.1 MVP 包含

- ✅ Agent CRUD（四个分区配置）
- ✅ Wiki 知识层编辑（ingest/update/synthesize/lint 工作流）
- ✅ 工具/MCP 配置（MCP 工具 + Wiki 查询工具）
- ✅ 路由规则配置
- ✅ Feedback 手动录入 + 查看 + 标签
- ✅ Feedback → wiki 蒸馏入口
- ✅ Release 提交 → 工单团队审批 → 发布
- ✅ Version 完整历史 + 一键回滚
- ✅ 三角色权限隔离
- ✅ 统一 Web UI（taste-skill 风格）

### 8.2 MVP 不包含（后续子项目）

- ❌ A 子项目：群聊 / Web / 工单系统的实时数据采集（MVP 反馈纯手动录入）
- ❌ C 子项目：跨 agent 问题总结、知识缺口自动发现、进化洞察
- ❌ 灰度发布
- ❌ 现场客户角色（第 4 角色）
- ❌ 对接系统 API 实时拉取反馈
