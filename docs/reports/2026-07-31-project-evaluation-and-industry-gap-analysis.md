## 一、项目总体评估

**一句话结论：设计成熟度显著高于实现成熟度。这是一个"管理壳"已经搭好、但"智能核"完全缺失的平台。**

| 维度 | 评级 | 证据 |
|------|------|------|
| 概念设计（三层 Loop / 四分区 / Release→Version） | ★★★★★ | MVP 设计文档完整、逻辑自洽 |
| 数据模型 | ★★★★ | `packages/db/prisma/schema.prisma` 626 行 30 个模型，覆盖全域 |
| 配置版本控制 | ★★★★ | `lib/versioning.ts` SemVer 自动计算 + 不可变快照 + 回滚，超过多数同类工具 |
| 数据持久化 | ★★ | Prisma schema 就绪但运行时全是 JSON 文件（`lib/data/store.ts`） |
| 认证 / RBAC | ★ | `/api/auth/login` 是 stub，身份从请求头透传，任何人可任意角色操作 |
| **LLM / 评测 / 复盘自动化** | **0** | **全项目没有一行 LLM 调用代码，没有 eval 框架，没有根因分析实现** |
| 可观测性 / 效果度量 | ★ | 仅 dashboard 聚合统计，无发布前后效果对比 |

**关键矛盾**：平台叫"Agent 持续改进"，但目前只能管理"改进的**记录**"（Feedback 单据、Release 审批单），不能执行"改进的**分析和验证**"。改进的智力劳动 100% 还在人脑里。

### 1.1 核心设计理念回顾（科普）

**三层 Loop（时间尺度分层的持续改进模型）**：

- **L1 即时交互环**（分钟级）：Agent 在岗解决工单，产出会话日志、评分、失败标记。L1 不在本平台构建，是改进数据的"源头"。
- **L2 产品改进环**（小时~天级，本平台核心）：反馈收集 → 根因分析 → 修改四分区配置 → Release 审批 → Version 不可变快照 → 支持回滚。
- **L3 智能进化环**（天~周级，规划中）：跨 Agent 洞察、共性缺口发现、知识自动蒸馏、共享概念池。

三层通过数据管道耦合：L1 的失败案例流入 L2 成为改进输入；L2 的版本上线回到 L1 生效；L2 的沉淀数据供 L3 做跨 Agent 分析，L3 的产出反哺 L2 的知识库。

**四分区 Agent 配置（一个 Agent = 一张配置卡）**：

| 分区 | 内容 | 类比 |
|------|------|------|
| Prompt | 系统提示词、角色设定、约束条件、输出格式 | Agent 的"性格与纪律" |
| Knowledge | 指向 Wiki vault，两层知识架构（蒸馏态知识优先，MCP 工具兜底查活数据） | Agent 的"长期记忆" |
| Tools | MCP 工具配置 + Wiki 查询工具（index/summary/grep/全页读取逐级升级） | Agent 的"手" |
| Routing | 工单分类规则、分派策略、转人工阈值、升级策略 | Agent 的"分诊台" |

**Release → Version 版本控制机制**：

- Release：一次改进的"申请单"（改进说明、变更分区、关联 Feedback、审批状态）。
- Version：审批通过后冻结四分区完整内容的不可变快照；语义化版本号自动计算（ROUTING 变更或多分区变更 → minor；单个非路由分区 → patch）；支持一键回滚。

**三角色权限模型**：工单团队（管理员，审批发布）/ 产品组（编辑者，改配置提发布）/ CRE（反馈者，录入改进建议）。

## 二、与行业最佳实践的差距

对照当前业界 Agent/LLM 应用持续改进的主流做法（LangSmith / Langfuse / Braintrust 类平台、OTel GenAI 语义规范、eval-driven development），差距按重要性排序：

### 差距 1：没有 Trace，复盘无据可依（最致命）

- **业界做法**：每次 Agent 交互记录完整 trace——用户 query、检索了哪些文档、每个文档的相关性得分、调用了哪些工具、工具返回什么、最终回答。复盘的第一步永远是"看 trace"。
- **本项目现状**：Feedback 只有 `source.sessionData` 一个自由文本字段，靠人手工粘贴会话片段。**没有检索轨迹，就无法回答"语料里有没有、检索到没有"这个复盘核心问题。**

### 差距 2：没有失败归因分类学（Error Analysis）

- **业界做法**：对失败案例做系统性归因（open coding → 归纳失败模式分类），每类失败对应不同的修复动作。"eval 之前先做 error analysis"是业界反复强调的纪律。
- **本项目现状**：Feedback 有 `tags`（KNOWLEDGE_GAP / TOOL_FAILURE 等）和 `targetPartition`，分类框架的骨架有了，但**归因过程纯靠人拍脑袋填**，没有任何辅助诊断。

### 差距 3：没有 Golden Set 和回归评测，发布审批是"盲批"

- **业界做法**：失败案例沉淀为评测集（golden dataset）；每次改动（prompt/语料/skill）发布前跑回归评测，用指标（回答正确率、检索命中率、RAGAS 类指标）作为发布门禁；发布后对比效果。
- **本项目现状**：Release 审批只看人写的 `changeNote` 和 diff——**审批人无法知道这次语料改动是否真的修复了那张工单，更不知道有没有把之前能答的问题改坏**。这是与业界最大的方法论差距。

### 差距 4：知识蒸馏 / 语料加强闭环只有数据模型，没有引擎

- **业界做法**：从失败 case 自动起草知识条目 → 人审 → 入库 → 验证，形成数据飞轮。
- **本项目现状**：Wiki 模型设计很好（provenance / lifecycle / tier / confidence，`WikiIngestJob` 都建了模），但蒸馏引擎、confidence 计算、wiki-lint 全部未实现。

### 差距 5：工程基线不达生产标准

无真实认证、JSON 文件存储无并发控制、无 CI/CD、审计日志写单文件。**但注意**：若平台近期是个人/小团队内部使用，这些债的优先级应低于差距 1-3。业界最佳实践也讲"匹配阶段"，不必为单用户工具先修 RBAC。

### 本项目做得比业界平均水平好的地方

- 配置四分区 + SemVer 版本快照 + 审批回滚，比多数团队"prompt 存在代码里随手改"要规范；
- Feedback 状态机（NEW→TRIAGED→…→CLOSED 合法转移表）、Wiki 页面元数据设计（provenance/lifecycle/tier）在概念上领先，只欠落地；
- 统一错误体系、Zod 全量校验、181 个测试 / 94% 语句覆盖的工程纪律。

## 三、工单复盘场景差距盘点

目标流程：**工单上下文传入 → 复盘"为什么没支持到" → 加强语料（工单 ack 库 / AI Stack 库，阿里云专有云产品）和 skills**。

| 流程环节 | 平台现状 | 缺口 |
|---|---|---|
| ① 工单上下文传入 | Feedback API 可收录（title/content/sessionData） | 缺结构化工单字段（工单号、产品、错误日志、Agent 会话/检索轨迹）；缺批量导入 |
| ② 复盘：为什么没支持到 | 只有人工填 tags 和 targetPartition | **无复盘引擎**。核心是区分五类归因：语料缺失 / 语料有但检索未命中 / 语料过期或错误 / skill 缺失或失败 / 超出 Agent 能力边界——五类的修复动作完全不同 |
| ③ 加强语料 | Wiki vault 模型完备，可建 DRAFT 页面走审批 | 外部真实语料库与平台内部 wiki-vaults（JSON mock）没有任何连接（无同步、无导入、无检索代理） |
| ④ 加强 skills | Skill 注册表 + 绑定关系齐全 | Skill 只是"登记卡片"，不能执行、不能测试，加强无从验证 |
| ⑤ 验证加强有效 | 无 | 无法回放失败工单验证"改完之后这张工单能不能答对了" |

**核心判断**：平台的表单和审批流对该场景是"可用的骨架"，但复盘、加强两个核心动作恰好都落在未实现的部分。另需先决策：外部语料库是**导入为 wiki vault 管理**，还是**作为外部知识源只管理"改进建议单"**——这决定后一半实现方式。

## 四、关键技术债与风险点

1. **安全风险**：无认证/授权，任何用户可篡改数据（内部单用户阶段可容忍，多人使用前必须补）。
2. **可扩展性风险**：JSON 文件无法支撑多实例部署和并发写入；评测集与 trace 数据量上来后必然撑不住。
3. **功能风险**：核心设计（蒸馏、自动采集、效果度量、Evaluator）未实现，平台价值打折。
4. **工程风险**：无 CI/CD、无监控告警、无数据备份；多人同时编辑同一 Agent 可能相互覆盖。

## 五、改进路线图与优先级矩阵

**面向工单复盘场景重排优先级**（不建议按"先修 auth/Prisma"的通用工程债顺序走）：

### P0 — 让复盘有据可依（1-2 周）

1. 扩展 Feedback 数据模型：增加结构化工单上下文（工单号、产品线、问题描述、Agent 实际回答、检索命中列表、skill 调用记录），提供批量导入 API/脚本。
2. 打通外部语料库的**检索探针**：给工单 ack 库、AI Stack 库各接一个查询接口（MCP 或 HTTP），让平台可以拿失败工单的问题去"回放检索"，回答"语料里到底有没有"。

### P1 — 复盘引擎（2-3 周，第一处该引入 LLM 的地方）

3. LLM 根因分析：输入工单上下文 + 回放检索结果，输出五类归因之一 + 证据 + 建议的 `targetPartition`，人工确认后写回 Feedback。
4. 归因聚合看板：按产品线/归因类别统计，发现共性缺口（如"AI Stack 库在某组件的排障语料系统性缺失"）。

### P2 — 加强闭环 + 回归验证（3-4 周）

5. 复盘产出直接生成**语料补丁草稿**（DRAFT wiki 页 / 外部语料库变更建议单）和 **skill 加强建议**，走现有 Release 审批流。
6. 失败工单自动沉淀为**评测集**：每张复盘过的工单变成一条 eval case；发布审批前自动回放评测集，给审批人看"本次改动修复 N 张 / 回归 0 张"——补上与业界最大的方法论差距。

### P3 — 工程债（按需）

Prisma/Postgres 落地、真实认证与 RBAC 强制、CI/CD、审计入库。

### 与既有路线图（2026-07-21 评估）的关系

原路线图 P0 = 鉴权 + Prisma + 审计（通用工程债优先）；本报告基于工单复盘场景将"复盘证据链 + 复盘引擎 + 回归评测"提到最前，工程债降为 P3 按需跟进。两者不冲突：使用规模扩大时，原 P0 项自动升级回高优先级。

## 六、总结

AgentUp 的产品价值，本质是**"把 Harness 工程纪律产品化给业务团队"**。当前 MVP 已经把"产品形"做对了（四分区 + Release + Version + 三层 Loop 概念），与业界最佳实践的核心差距集中在**证据链（trace）、归因（error analysis）、验证（golden set 回归评测）**三件事上——恰好也是工单复盘场景最需要的三件事。下一步应沿"复盘有据 → 归因有理 → 加强有验"的主线补齐智能核。
