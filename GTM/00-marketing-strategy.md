## 一、市场洞察与竞争格局

### 1.1 市场背景：Agent 的瓶颈从「上线」移向「改进」

- 模型能力（MaaS）快速商品化，企业落地 Agent 的门槛在下降；但上线之后的**持续改进**仍是手工作坊：prompt 藏在代码里、改动无审批、效果无度量、出事靠记忆回滚。
- 行业术语正在成形（AgentOps / LLMOps），但主流工具聚焦「搭建」或「观测」，以**改进闭环为中心**的轻量开源方案存在空位。
- 专有云/私有化场景（数据不出域）对第一方、可自部署、模型中立的平台有刚性需求。

### 1.2 竞争与替代格局（诚实版）

| 阵营 | 代表 | 他们管什么 | 不管什么（= 我们的位置） |
|------|------|-----------|--------------------------|
| 自研脚本 | prompt 存代码 + 群里贴反馈 | 能跑起来 | 审批、快照、效果度量、回滚 |
| 低代码 Agent 平台 | Dify / Coze / 百炼应用编排 | 搭建与调用 | 改进运营闭环（反馈归因→审批→效果报告→回滚） |
| LLM 可观测平台 | LangSmith / Langfuse | trace 与评估 | 配置的版本化发布与审批治理 |
| **agent-up** | 本项目 | **改进闭环本身** | 不做模型托管、不做低代码编排、不做通用 APM |

**定位纪律**：对竞品只说「互补与空位」，不做贬损性对比；上表每一行「不管什么」都必须经得起对方官网核对。

### 1.3 SWOT（制定策略用，不对外）

| | 有利 | 不利 |
|---|------|------|
| **内部** | 闭环完整度（反馈→归因→审批→效果→回滚）；工程纪律证据链（508 测试 / 覆盖率门禁 / CI 双矩阵）；模型中立实证（MiMo 真实接入）；MIT 开源可自部署 | 单人维护；无生产级多租户/认证；README 全中文（国际渠道受限）；无真实企业标杆案例 |
| **外部** | AgentOps 品类认知红利；专有云私有化需求；开源获客成本低 | 大平台可能向下补齐闭环；品类教育成本；LLM 平台绑定倾向 |

## 二、STP：细分、目标与定位

### 2.1 市场细分与优先级

| # | 细分 | 规模判断 | 优先级 | 理由 |
|---|------|---------|--------|------|
| S1 | 已部署工单/客服 Agent 的企业团队（专有云或公共云） | 中 | **P0** | 痛点最锐利，付费意愿明确，POC 路径最短 |
| S2 | 开源开发者 / Agent 爱好者 | 大 | **P0**（获客侧） | 低成本流量与贡献入口，反哺 S1 线索 |
| S3 | 求职者市场（全栈/解决方案架构方向的个人品牌） | 小 | P1 | 维持即可，物料已齐（02） |
| S4 | 模型/云生态伙伴（MaaS、推理服务方） | 中 | P1 | 联合叙事放大器，非直接客户 |

### 2.2 ICP 与画像（Persona）

**ICP（S1 企业侧）**：已有一个以上生产 Agent（工单/客服/运维问答类）、模型走公共云 API 或专有云私有化、团队里有「产品组负责人 + CRE/算法 + 工单团队」三方协作结构的组织。**最锐利信号**：客户最近一次改 prompt 走了发版流程，或出过「改完更差但说不清」的事故。

| Persona | 角色 | TA 的日常痛点 | 关心什么 | 对应叙事支柱 |
|---------|------|--------------|---------|-------------|
| 采购发起人 | Agent 平台负责人 | 每次改进都要排研发档期 | 降本、风险可控、可向上汇报 | 管得住 + 算得清 |
| 使用者 | CRE / 算法工程师 | 反馈与配置改动之间没有结构化通路 | 归因准不准、试改快不快、回滚稳不稳 | 看得见 + 退得出 |
| 侧翼影响者 | 工单团队主管 | 改进意见提了没人接 | 反馈有没有下文 | 看得见 |
| 生态伙伴 | MaaS/云架构师 | 客户问「买了模型之后怎么越用越好」 | 有没有可讲述的模型消费治理故事 | 双形态 + 模型中立 |

### 2.3 定位声明（Positioning Statement）

**Geoffrey Moore 跨越鸿沟模板**：

> 对于**需要持续运营生产级 Agent 的企业团队**（目标客户），他们苦于**改不动、不敢改、说不清**（需求），
> **agent-up** 是一个**开源的 Agent 持续改进平台**（品类），
> 它把「反馈 → AI 归因 → 改配置 → 审批发布 → 效果报告 → 一键回滚」做成**工程化闭环**（核心利益）。
> 与低代码搭建平台和 LLM 观测工具不同（替代方案），agent-up 只做**改进闭环本身**，模型中立、可私有化、每一步都有审计（关键差异）。

**April Dunford 五要素落表**：

| 要素 | 内容 |
|------|------|
| 替代方案 | 自研脚本 / 低代码 Agent 平台 / LLM 观测平台 |
| 独特能力 | 反馈→发布→效果→回滚的全闭环 + 不可变版本快照 + append-only 审计 + 模型中立网关（MiMo 实证） |
| 市场品类 | Agent 持续改进平台（AgentOps） |
| 关键利益 | 改得动、敢改、说得清——且改坏了一步退回 |
| 目标人群 | S1 企业团队（先）与 S2 开发者（放大） |

## 四、分受众叙事方案（All Product Narratives）

> 每个叙事方案五要素：**目标 / 一句话 / 30 秒电梯 / 关键信息点与 CTA / 渠道与禁忌**。
> 30 秒电梯均需与 [02 面试话术](./02-interview-playbook.md)的主电梯陈述同源（同一闭环、不同收尾）。

### 4.1 叙事 A：企业客户——「把 Agent 的持续改进从手工作坊变成生产线」

- **目标**：把演示邀约转化为 POC（1 个产品组 + 1 个 Agent + 4 周闭环跑通）。
- **一句话**：你的 Agent 上线只是开始；agent-up 让它每周都在变好，而且每一步都有审批、有快照、有报告。
- **30 秒电梯**（主版本，见 02）：
  > 企业把 Agent 上线只是开始，真正的难点是持续改进。agent-up 把改进做成了工程化闭环——反馈进来由大模型自动归因到四个配置分区，改配置走审批发布生成不可变快照，上线 7 天自动出效果报告，改坏了一键回滚。模型层可插拔：公共云走百炼、专有云走 Apsara Stack，同一套闭环两种形态。
- **关键信息点**：三痛点开场（改不动/不敢改/说不清）→ 闭环动线 → 双形态 → 诚实边界主动声明。
- **CTA（三档）**：① 8 分钟现场演示（动线见 [01](./01-customer-one-pager.md)）；② 自助演示站 https://qtb3subkcwy5.meoo.fun（MOCK 登录）；③ 会后 48 小时内发出 POC 范围定义模板。
- **渠道**：客户现场 / 线上会议 + 会后留档（01 One-Pager + 04 FAQ）；行业社群定向分享。
- **禁忌**：不承诺 SLA 与生产可用性（明说「生产化路线有里程碑」）；不用演示数据冒充实测；不替客户估算 ROI 数字（口径表没有的数字不出现）。

### 4.2 叙事 B：开源社区——「Agent 改进方法论不该锁在黑盒平台里」

- **目标**：GitHub 关注与首批 issue/PR；建立「工程纪律标杆」的技术品牌；为 S1 线索蓄水。
- **一句话**：一个把「反馈→归因→审批→发布→效果→回滚」做成工程闭环的开源 Agent 持续改进平台，MIT、可自部署、模型中立。
- **30 秒电梯**：
  > agent-up 是 MIT 开源的 Agent 持续改进平台：改 Agent 配置不用发版，走审批和不可变快照；用户反馈由 LLM 自动归因到该改哪个分区；上线 7 天自动出效果报告；改坏了一键回滚。全仓 508 个测试、覆盖率门禁由 CI 强制，SQLite 单文件零依赖起服务，clone 下来八分钟能跑通全流程。
- **关键信息点**：
  1. **痛点共鸣开场**：「你的 prompt 还躺在代码里吗」——用三痛点做社区共情钩子；
  2. **工程纪律即卖点**：对工程师受众，508 测试 / 覆盖率 80·80·80·70 硬门禁 / Node 双矩阵 CI / 覆盖率只升不降的仓库纪律，本身就是内容题材与信任凭证；
  3. **零门槛上手**：`pnpm install` 起服务（SQLite 零守护进程）+ 在线演示站兜底；
  4. **模型中立实证**：演示环境真实接小米 MiMo，换模型只换配置——「不绑定任何一家模型」。
- **CTA**：GitHub star / clone 跑通 README 快速开始 / 用 issue 模板反馈（bug/feature 已配齐）/ PR 欢迎（CONTRIBUTING 已配齐）。
- **渠道（中文首发，国际二期）**：掘金首页投稿、知乎专栏、V2EX「分享创造」、开源中国收录、微信技术群；二期评估 HN（Show HN）/ Product Hunt / Reddit（需英文 README 短版，见 backlog B3）。
- **禁忌**：不刷 star 不买量；不在同一天多渠道重复轰炸同一篇原文（改写适配各社区语气）；演示账号口令只出现在演示站语境，不进入正式 README 主文。

### 4.3 叙事 C：面试与个人品牌——「一个能证明全栈工程与产品思维的完整作品」

- **目标**：面试通过率与个人技术品牌沉淀（维护即可，不扩张）。
- **一句话**：我用一个 508 测试、CI 全绿、真实接大模型的开源项目，完整演示「发现问题→设计闭环→工程落地→持续验证」。
- **30 秒电梯**：直接复用 [02 面试话术](./02-interview-playbook.md)主版本（本叙事是其管理源头，勿另造口径）。
- **关键信息点**：按岗位切换侧重（全栈 SA 讲工程纪律与可测试性设计；MaaS SA 讲模型消费治理与双形态）；两分钟版「怎么验证」数字必须实时对齐口径表。
- **CTA**：演示站 + GitHub 仓库链接（简历/主页常驻）。
- **渠道**：简历、面试现场、个人主页。
- **禁忌**：不把 MOCK 业务数据说成真实客户案例；被问生产化距离时按 02 的「三件事是真的」框架诚实作答。

### 4.4 叙事 D：生态合作——「模型消费的治理层，天然是模型的伴生需求」

- **目标**：与 MaaS/推理服务方（阿里云生态、小米 MiMo 等）形成联合讲述与互推。
- **一句话**：卖模型是第一步；agent-up 是让客户的模型消费「持续且可解释」的那层——用量有归因、改进有审批、效果有报告。
- **30 秒电梯**：
  > 客户买了模型之后，真正决定续费的是「越用越好」的体感。agent-up 站在模型网关之上做改进治理：AI 归因、发布审批、每 Agent 的真实用量聚合、效果报告。我们已用 MiMo 实证网关可插拔——对模型伙伴来说，这是把「调用量」变成「改进案例」的叙事放大器。
- **关键信息点**：模型中立网关（OpenAI 兼容协议）/ 每 Agent 用量聚合口径 / 双形态部署矩阵（`/maas` 页即为此叙事做的展品）。
- **CTA**：联合演示（我方出改进闭环，伙伴出模型侧）/ 内容互推一篇。
- **渠道**：伙伴技术沙龙、联合方案页、生态社群。
- **禁忌**：不替伙伴承诺商务条款；引用伙伴产品名时只用其官方口径（如百炼/Apsara Stack 的能力描述须与其官网一致）。

### 5.2 竞争对比话术（问「为什么不用 X」时）

统一应答框架（源自 02 Q2，可扩展不可改写结论）：
1. **定位互补不竞争**：模型平台管「调用」，观测平台管「看」，agent-up 管「改进运营」；
2. **闭环完整性**：表单式 prompt 管理与改进闭环的差别，是「有没有审批记录和效果报告」的差别；
3. **工程保证**：状态机拒绝非法流转、不可变快照、append-only 审计——不是 UI 约定，是数据层约束。

### 5.3 诚实边界：把「主动声明 MOCK」做成信任资产

这是本项目区别于常见营销的**方法论级差异**，在所有叙事中主动使用：
- 话术模板：「演示环境是 mock 数据 + 真实 LLM 的混合形态，页面有徽标可查——我们不把没做到的事说成做到了。」
- 底层逻辑：向企业客户卖「治理与审计」的平台，自己的对外材料首先经得起审计。
- 红线：任何物料出现「生产级/SLA/已服务客户 N 家」类表述前，必须先在口径表有实测依据，否则不得出现。

## 九、口径纪律与红线（营销治理）

1. **数字唯一事实源**：[GTM/README 事实口径表](./README.md#事实口径对外数字必须与实测一致)。项目数字变化 → 先改表 → 再同步本纲与 01–04/W1（表的更新命令已内置）。
2. **能力表述三禁**：禁「生产级/SLA/高可用」（未实测）；禁「已服务客户」（无案例）；禁「行业第一/最先进」（不可证）。
3. **MOCK 声明强制**：所有含演示截图/数据的物料必须携带 MOCK/LIVE 边界说明（模板见 5.3）。
4. **竞品表述**：只描述对方公开能力与我们的定位差异，不使用贬损措辞。
5. **安全相关**：演示账号口令仅用于演示语境；任何渠道不得引导用户把演示站当生产环境（SECURITY.md 已定义边界）。
6. **个人隐私与凭据**：物料中不出现真实客户名、真实凭据；MiMo 探针等实测数字必须带测试日期。
