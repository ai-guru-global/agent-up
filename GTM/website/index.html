01Agent 上线之后，改进为什么这么难？

这是我们在客户现场反复看到的三件事——它们决定了 Agent 是「越用越好」还是「上线即巅峰」。

1.改不动 现状的改进建议躺在 IM 里，落地靠下次大版本 Prompt 写在代码仓库里，改一句话要排期发版；业务同学提的改进意见，永远排不进迭代。
2.不敢改 现状的「上次那句是谁改的来着？」 改完不知道会不会更差：没有审批、没有版本快照，出了问题只能靠 git 记忆和人的经验回滚。
3.说不清 现状的汇报时只有截图，没有负向率变化 上线后效果靠感觉。「这次改进值不值」拿不出数据，模型预算与选型都对不齐。

02一条看得见、管得住、算得清、退得出的改进闭环

不是又一个 prompt 编辑器。是从「用户反馈」到「效果验证」的完整工程链路——每一步都有系统兜底。

01看得见

每条负向反馈进来，真实大模型调用自动归因：问题出在 Prompt / Knowledge / Tools / Routing 哪个分区，为什么，怎么改——直接给出可执行建议。实测锚点 · fb-001 → 归因 KNOWLEDGE 分区

02管得住

配置变更提交 Release 审批：自动 diff 上一版本，AI 生成变更摘要与风险提示；通过即产生不可变版本快照，谁改的、改了什么，审计日志一条不少。实测锚点 · 0.2.0 · pm-chen 提交 → admin-zhao 审批通过

03算得清

版本上线满 7 天自动聚合效果报告：反馈量、负向比、严重度分布；改完配置还能在试聊 Playground 用当前配置立即验证——不等上线再赌。实测锚点 · 报表样式见「实测实录」

04退得出

分区级或整版本一键回滚：改坏知识库不用动提示词，回滚本身写审计。回退从「事故预案」变成「日常动作」。

08我们把真与假的边界印在界面上

企业软件最贵的成本是「信错」。所以每个页面都自带徽标——这是我们与 PPT 产品的区别。

MOCK

业务数据 = 演示种子

Agent / 反馈 / 发布记录来自本地种子数据（未接真实数据库），琥珀色徽标逐页标注。生产化路线明确：Prisma 持久化 → 真实认证 → CI。

LIVE

AI 能力 = 真实调用

连通性探针、反馈归因、变更摘要、试聊 Playground 四处均为实时大模型调用，绿色 LIVE 徽标标注，并展示时延与 tokens 用量。

为什么主动说这个？因为在客户现场，「哪里是真的、哪里是演示」必须 10 秒内说清楚。 我们把边界做成了 UI 的一部分——这本身也是产品方法论：改进的前提，是对现状诚实。

本页数字口径 · 232 测试 / 30 路由 / 4×LIVE 为项目实测统计；2,557ms 与 tokens 为 2026-08-25 MiMo 实测；反馈、发布与报表数值为演示种子（MOCK）。
