No.01痛点 · PAIN

Agent 上线之后，改进为什么这么难？

这是我们在客户现场反复看到的三件事——它们决定了 Agent 是「越用越好」还是「上线即巅峰」。

1

改不动

Prompt 写在代码仓库里，改一句话要排期发版；业务同学提的改进意见，永远排不进迭代。

现状的典型样子改进建议躺在 IM 里，落地靠下次大版本
2

不敢改

改完不知道会不会更差：没有审批、没有版本快照，出了问题只能靠 git 记忆和人的经验回滚。

现状的典型样子「上次那句是谁改的来着？」
3

说不清

上线后效果靠感觉。「这次改进值不值」拿不出数据，模型预算与选型都对不齐。

现状的典型样子汇报时只有截图，没有负向率变化
No.02方案 · THE LOOP

一条看得见、管得住、算得清、退得出的改进闭环

不是又一个 prompt 编辑器。是从「用户反馈」到「效果验证」的完整工程链路——每一步都有系统兜底。

01看得见

每条负向反馈进来，真实大模型调用自动归因：问题出在 Prompt / Knowledge / Tools / Routing 哪个分区，为什么，怎么改——直接给出可执行建议。

02管得住

配置变更提交 Release 审批：自动 diff 上一版本，AI 生成变更摘要与风险提示；通过即产生不可变版本快照，谁改的、改了什么，审计日志一条不少。

03算得清

版本上线满 7 天自动聚合效果报告：反馈量、负向比、严重度分布；改完配置还能在试聊 Playground 用当前配置立即验证——不等上线再赌。

04退得出

分区级或整版本一键回滚：改坏知识库不用动提示词，回滚本身写审计。回退从「事故预案」变成「日常动作」。

No.06演示 · LIVE DEMO

8 分钟，把闭环走一遍

以下每一步都是真实系统操作（非录屏）：MOCK 数据有徽标，真实模型调用有 LIVE 徽标。

STEP 1 · 约 1 分钟

证明「模型是活的」

打开 /maas 点「发起真实调用」——实时返回模型身份、时延与 tokens。平台连接的不是截图，是正在运行的推理服务。

STEP 2 · 约 1.5 分钟

反馈进来，AI 归因

在 /feedback 挑一条 NEGATIVE 反馈点「AI 归因」——LLM 指出问题在哪个分区、理由、怎么改。

STEP 3 · 约 2 分钟

改配置，立即验证

按归因建议在 /agents/ecs-assistant 修改 Prompt 分区，保存后在「试聊 Playground」用当前配置当场试聊——改完即验，不赌上线。

STEP 4 · 约 2 分钟

审批发布，AI 把关

/releases 提交发布 → 查看自动 diff + 「AI 变更摘要」（影响面与风险）→ 审批通过，生成不可变版本快照。

STEP 5 · 约 1.5 分钟

效果报告与回滚底气

版本历史里看 7 天效果报告徽标；顺手演示「回滚此分区」——改坏了，一步退回去，回滚本身有审计。

No.07边界 · HONESTY

我们把真与假的边界印在界面上

企业软件最贵的成本是「信错」。所以每个页面都自带徽标——这是我们与 PPT 产品的区别。

MOCK

业务数据 = 演示种子

Agent / 反馈 / 发布记录来自本地种子数据（未接真实数据库），琥珀色徽标逐页标注。生产化路线明确：Prisma 持久化 → 真实认证 → CI。

LIVE

AI 能力 = 真实调用

连通性探针、反馈归因、变更摘要、试聊 Playground 四处均为实时大模型调用，绿色 LIVE 徽标标注，并展示时延与 tokens 用量。

为什么主动说这个？因为在客户现场，「哪里是真的、哪里是演示」必须 10 秒内说清楚。 我们把边界做成了 UI 的一部分——这本身也是产品方法论：改进的前提，是对现状诚实。
